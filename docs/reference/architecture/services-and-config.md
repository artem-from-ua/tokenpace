# Architecture — services, config, and Settings

The cross-cutting picture is in [overview.md](overview.md). Here — the second independent stream
(service status, now for **two** providers), the monitored-services config, persistence/migration,
the Settings window, the log archiver, and the Troubleshoot window.

## Claude service status (#31)

A second stream, independent of usage — and since [ADR-0119](../../adr/0119-status-polling-own-cadence-and-backoff.md)
independent in the literal sense: it runs on **its own** `LivePollScheduler`, holds **its own** 429
backoff, and no longer needs a usage tick to exist. When `StatusCadence.isDue` (interval = the
politeness floor, stretched to the usage interval when one is running and slower, and overridden
outright by an active `Retry-After` hold), the agent calls `status.claude.com/api/v2/summary.json`, decodes
`components[]` and `incidents[]`, resolves the former into logical services (`MonitoredServices`),
and draws one row per monitored component in the popup — when there's a problem or the component
went green less than 15 minutes ago. The most serious problem → a single dot in the menu bar.

**Service state is determined exclusively by `components[].status`** — no incident field affects
it (ADR-0013 §2 still stands; ADR-0071 §1 only narrows it). Each row carries its state's age from
`components[].updated_at`: the field shifts exactly on a status change, so the age comes from the
API and survives a restart mid-outage, unlike a homegrown counter.

## GitHub service status — the second provider (#454, ADR-0121)

A **second status endpoint**, `www.githubstatus.com/api/v2/summary.json`, polled by a loop of its
own. GitHub runs the same Statuspage v2 schema, so `StatusSummary` decodes both pages without a
second decoder; what is per-provider is everything around it.

**Status only.** GitHub publishes no subscription limit the bars model, so there is no usage half,
no second `PollingEngine`, and no `Token limits usage` section on its Settings page — the asymmetry
with Claude is the design, not a gap ([ADR-0121](../../adr/0121-github-as-a-status-only-provider.md)).

**One logical service, `ServiceID.githubDevelopment` ("Development services")**, resolving five
components verbatim by name — `Git Operations`, `API Requests`, `Issues`, `Pull Requests`,
`Actions` — aggregated worst-of-5 under a single toggle. The other seven components the feed carries
(`Copilot`, `Copilot AI Model Providers`, `Packages`, `Pages`, `Codespaces`, `Webhooks`, and the
non-service row literally named `Visit www.githubstatus.com for more information`) are never
selected and need **no filter**: matching is by exact name, so a component we do not ask for cannot
arrive.

**Its own loop, its own everything** — the per-source shape
[ADR-0119](../../adr/0119-status-polling-own-cadence-and-backoff.md) built, now occupied by its
second tenant. GitHub has its own `LivePollScheduler` on its own `SignalHub.Subscriber` key, its own
`PollingBackoff`, its own `lastGitHubSuccess` marker, its own in-flight task, and its own visible-
incident list. Nothing is shared: a `429` from `githubstatus.com` holds only this source, an
unreachable GitHub greys only its own rows (`StatusHealth.unknownGitHub`), and a Claude incident
cannot drag this poll to the 60-s problem floor against a third party's page — which is why
`StatusCadence` is fed `worstProblem(of: .github)`, never the flattened `worstProblem`.
`usageInterval` is always `nil` here (no usage poll to settle with — the case ADR-0119 made the
parameter optional for), and the `User-Agent` is `TokenPace/<version>`, never `claude-code/<version>`.

**The loop polls once before its first wait.** `waitForNextPoll` sleeps the whole interval up front,
so waiting first would leave the plate empty for the five-minute politeness floor after every launch
— a monitored provider showing nothing, the exact state the header dot exists to rule out. Claude
never had this problem because its status also rides the usage tick.

**The two healths merge at render time**, not into a stored value: they arrive on independent
cadences, so a stored merge would be rewritten by whichever poll landed last and the loser's checks
would flicker out until its own next poll. `AppDelegate.renderedStatusHealth` folds them with
`StatusHealth.merging(_:)`, which **replaces** a provider's checks rather than accumulating them
(idempotent, and display order stays Claude-first regardless of who polled last).

**`isMonitoringAnything` spans providers.** `ProviderMonitoring`'s property of that name answers only
for Claude — it is `claudeApiLocked` under another name. `AppDelegate.isMonitoringAnything` ORs it
with `PersistedConfig.githubMonitoring.isMonitoringAnything`, without which a GitHub-only
configuration would draw the popup's "Monitoring is off" dead end over a live GitHub plate and put
the nothing-monitored glyph in the menu bar during a GitHub outage.

**Incidents** are filtered against **each provider's own** monitored names
(`StatusHealth.monitoredGitHubComponentNames`), never a crossed set — a generic name like `Issues`
exists on both pages. The two lists are kept apart for the same reason the healths are, and
concatenated for exactly one reader: the episode subscription and the banners it drives, where the
provider does not change what the banner says. That is what makes GitHub incidents flow through the
**existing** notification mechanism with no toggle of their own. The popup is deliberately *not* that
reader — each plate renders only its own list.

**Settings:** `Providers › GitHub` (`ProvidersGitHubPane`) carries one `Monitored services` section
with the single `Development services` toggle, and nothing else — no usage section, and no
provider-level master switch (with one service the service switch *is* the provider switch). Its row
on `ProvidersPane` wears the **same `cloud.fill`** Claude's does on `ColorRole.githubBrand` (pure
black; ADR-0094 §7's derived gradient puts the far end at `#606060`) — one glyph for the category,
colour for the identity. The popup's header mark uses `ColorRole.githubBrandInk` instead, which
resolves per appearance, because black ink on the dropdown's dark material is unreadable.

## Incidents and episode subscription (#279, ADR-0071)

A layer on top of the previous stream: incidents as **context** and a **subscription target**,
never as a source of state. The same `summary.json` already carries `incidents[]` in full (along
with their `components[]` and `incident_updates[]`), so a second endpoint isn't needed.

`IncidentVisibility` filters in four steps: closed → gone; ones whose components don't intersect
the monitored set → gone; ones whose monitored components are already green → gone (the measured
gap between going green and `resolved` — 6 min median, up to 480 min); ones older than the
configured threshold → gone.

In the popup, **⌥ switches the dimension**: service rows are replaced with incident rows
(description + `age · stage` on the right of the last line, the stage links to the specific
incident). The subscription is **one per episode**, not per ticket: the user subscribes when they
see their services are down and has no way to know which of several incidents is affecting them.
An episode ends when all monitored components are green **or** all active incidents have moved to
`monitoring`; both transitions are debounced because components flicker. Event deduplication is by
`incident_updates[].id`.

## The Troubleshoot window (ADR-0020)

The ⌥-Option-gated "Troubleshoot…" item opens a large, resizable `.normal`-level window with
live per-poll updates: update interval + token (read/expires) + the raw usage-API response
(pretty-printed JSON / error payload + HTTP status + timestamp). Diagnostics flow through the pure
`PollDiagnostics` pipeline.

| **StatusPayloadFingerprint / StatusPayloadLog** | A fingerprint of the "material" part of the payload (sorted component statuses + each incident's `id`/stage/`update.id` set) and a dev JSONL log that writes raw bodies only when the fingerprint changes. | **IncidentNotificationDelegate** | `UNUserNotificationCenterDelegate` (shell): clicking the banner opens the incident page, the "Unfollow" action drops the subscription. **Not** `@MainActor` — UN calls the delegate on its own queue, and `@MainActor` code there triggers `dispatch_assert_queue` (the same trap described in `BackToWorkNotifier`) |
| **StatusCadence** | A pure seam for the polite frequency (`TokenPaceKit`): `interval = max(floor, usageInterval ?? 0)`. Since ADR-0119 the **usage interval is optional** and can only slow polling down, never speed it up — with no usage tick the interval collapses to the floor, which is the standalone cadence a lone status source needs. The **timer is the loop's own** `LivePollScheduler` (the usage tick is now a second, opportunistic entrance through the same `isDue` gate). **Two floors:** `floor` = 5 min (everything operational); `problemFloor` = 60 s (as soon as *that source* has a problem — the flag is passed in per source, never read from a flattened value). Above both, `nextInterval(backoff:…)` gives an active 429 hold absolute priority, mirroring the usage loop's `429 hold > idle > base`. ADR-0013, ADR-0119 |
