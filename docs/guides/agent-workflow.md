# Робочий процес AI-агента

Операційні правила для AI-агента (Claude Code та ін.), що працює в цьому репозиторії. Це доповнення
до критичних правил у [../../CLAUDE.md](../../CLAUDE.md): тут — конкретні звички роботи, зібрані з
досвіду сесій. Секрети й конкретні ідентифікатори (Apple ID, GitHub Project node-IDs тощо) тут
**навмисно відсутні** — вони не належать репозиторію.

Термін «мейнтейнер» нижче означає власника репозиторію, який запускає застосунок і перевіряє зміни
вживу.

> ## ⚠️ Прямі заборони живуть у CLAUDE.md, не тут
>
> Категоричні «ніколи не роби X» (`pkill` на TokenPace, `defaults delete` домену, dev-`.app` у
> `/Applications`, конкурентний `log stream`, коміт у `main`) перенесені до
> [§ «Заборони, які не можна порушити»](../../CLAUDE.md) — і це не косметика.
>
> **Файли з `docs/` не завантажуються в контекст автоматично.** Поки заборони жили тільки тут,
> CLAUDE.md лише посилався на них, і в момент дії агент їх не бачив — саме так у сесії 2026-08-17
> тричі виконано `pkill -f "TokenPace"`, що поклало нотаризовану копію мейнтейнера. Заборона була
> прочитана на старті сесії й усе одно не спрацювала, бо була **не там, де приймається рішення**.
>
> Отже: **чинний текст заборон — у CLAUDE.md.** Тут лишається деталізація, обґрунтування й історія
> порушень (вони цінні як пояснення *чому*). Додаєш нову заборону — пиши її в CLAUDE.md, а тут за
> потреби розгортай.

## Гілки, PR і синхронізація main

- **Ніколи не комітити напряму в `main`.** Робота — через feature-гілки (`<prefix>/<kebab>`,
  префікси: `feature` / `bugfix` / `hotfix` / `release` / `docs` / `test` / `chore` / `refactor`) і
  PR проти `main`. **Не stacked** — кожен PR проти `main`, не проти іншої feature-гілки.
- **Перед `gh pr create` перевір, чи `main` не зрушив.** `git fetch origin main`; якщо `main`
  просунувся від merge-base гілки — **зроби rebase на `origin/main` і розв'яжи конфлікти перед PR**,
  не відкривай PR проти застарілої бази.
- **Семантичні колізії, які git не позначить конфліктом:** дві гілки, що додають **той самий
  наступний номер ADR** (чи індекс міграції), треба перенумерувати — навіть якщо мержиться чисто.
- **Синхронізація локального `main`** (коли він відстав від `origin/main`): лише **fast-forward**
  (`git merge --ff-only origin/main`), лише при **чистому дереві**, і **лише в головному чекауті** —
  ніколи не автопулити всередині worktree (автоматичний pull на feature-гілці посеред роботи може
  дати merge-коміт чи конфлікт поверх незакомічених змін). Якщо ff неможливий чи дерево брудне —
  зупинись і повідом, не мерж і не stash автоматично.

## Worktrees

Фонові сесії ізолюються у git-worktree (`EnterWorktree`). Три шорсткості, усі лікуються
дисципліною, а не конфігом:

1. **Негарне ім'я гілки.** `EnterWorktree` бере `feature/foo`, додає префікс і замінює `/`→`+` →
   `worktree-feature+foo`. Одразу після входу перейменуй гілку за конвенцією:
   `git branch -m feature/foo`.
2. **Edit/Write заблоковані в головному чекауті** поки фонова сесія ізольована. Тому **всі
   merge/rebase запускай усередині worktree** (де Edit працює), а потім fast-forward `main` /
   push гілки. Не веди конфліктну git-операцію з головного чекауту під час фонової сесії.

   **Найчастіша помилка сесії — абсолютний шлях у головний чекаут.** `Edit` із
   `/Users/…/devel/cc-timer/docs/…` відбивається («Edit the worktree copy of this file instead of
   the shared-checkout path»), бо файл треба правити в
   `/Users/…/devel/cc-timer/.claude/worktrees/<назва>/docs/…`. Пастка в тому, що **читання
   проходить**: `grep`/`sed` за коротким шляхом розгортаються в cwd (= worktree), а в `Edit`
   підставляється абсолютний шлях із пам'яті — і він веде не туди. За вимірами по всіх сесіях цього
   проєкту таких відмов **47**. Ліки: у `Edit`/`Write` бери шлях **із виводу попереднього
   `grep`/`Read`**, а не з пам'яті; коли сумніваєшся — `git rev-parse --show-toplevel`.
3. **`gh pr merge --delete-branch` падає ПІСЛЯ мержу — і лишає віддалену гілку.** У worktree
   `main` уже зайнятий головним чекаутом, а `--delete-branch` видаляє й **локальну** гілку, для чого
   `gh` мусить спершу перемкнутися на базову. Git відмовляє («main вже використовується робочим
   деревом»), `gh` вмирає — але **мерж на GitHub уже пройшов**. Помилка виглядає так, ніби мерж не
   вдався; не перезапускай його. Роби так:
   ```sh
   gh pr merge <N> --squash                    # без --delete-branch
   gh pr view <N> --json state --jq .state     # переконайся: MERGED
   git push origin --delete <branch>           # віддалену гілку прибери сам
   ```
   Якщо `--delete-branch` уже передано й видно помилку — **спершу перевір `gh pr view`**: мерж
   майже напевно відбувся, лишилось прибрати гілку.

Ізоляція worktree корисна (паралельні фонові задачі не топчуть чекаут) — **не вимикай**
`worktree.bgIsolation`. Повний escape-hatch `bgIsolation: none` існує, але це остання інстанція, не
бажаний фікс.

## Запуск застосунку для перевірки UI

- Для живої перевірки menu-bar / Settings запускай dev-збірку **прямо через `swift run`**:
  `TOKENPACE_STUB=… swift run TokenPace` (фоновий job — ок). Якщо статус-айтем не з'явився — **вбий
  застарілий dev-PID і перезапусти `swift run`**.
- **Ніколи не збирай dev-`.app` у `/Applications` за власною ініціативою.** Мейнтейнер запускає
  встановлений реліз саме звідти; dev-бандл там **перезапише його реліз** незнаковою збіркою —
  деструктивна, зовнішньо видима зміна, якої він не просив.
  **Коли просить — роби.** «Перевстанови», «онови мою копію», «постав свіжий білд» = дозвіл на весь
  ланцюжок (зупинити стару копію, замінити бандл, запустити нову) — див. ✅-виняток у
  [§ Зупинка застосунку та логи](#зупинка-застосунку-та-логи).
- **Кілька іконок TokenPace у menu bar — це очікувано й правильно**, не «виправляй» це вбивством
  релізу. Одночасно можуть бути: нотаризований реліз із `/Applications` **плюс декілька dev-копій**
  з різними стубами, запущених із різних сесій Claude Code. **Усі звуться `TokenPace`.**
- ⚠️ **Скриншот-автоматизація (AX / `osascript` / System Events) НЕ вміє відрізнити інстанси.**
  `click menu bar item 1` наослі́п відкриває Settings/меню **якогось** TokenPace — легко релізу чи
  *чужої* dev-копії, не тієї, що з твоєю зміною. Скрин тоді показує не ту збірку, або вікно «не
  знаходиться» у твоєму процесі. Тому:
  - **не клікай menu-bar-item за іменем/індексом** для відкриття dropdown/Settings;
  - навіть `pgrep -f '\.build/debug/TokenPace' | head -1` бере *якийсь* dev-PID — якщо копій кілька,
    звужуй за **власним** PID (`$!` від свого `&`-запуску), не за іменем;
  - **dropdown (NSMenu) узагалі не скриншотиться надійно** — menu-tracking блокує; **Settings** —
    лише якщо гарантовано влучив у свою dev-іконку. Надійний шлях: **віддати мейнтейнеру** відкрити
    саме потрібну dev-збірку й перевірити вживу (це й є канонічна UI-верифікація перед PR).
- Тимчасовий `.app`-бандл потрібен лише для фіч, залежних від підпису (launch-at-login /
  SMAppService, апдейт-сигнали) — і навіть тоді не в `/Applications` без явного дозволу. Деталі й
  перелік стубів — у [ui-verification.md](ui-verification.md).

## Зупинка застосунку та логи

- 🚫 **Не твоє — не зупиняй. Ніколи.** Вбивати можна **виключно** той процес, який **ця сесія сама
  запустила** й чий PID вона зберегла при старті. Будь-який інший інстанс TokenPace — нотаризований
  реліз мейнтейнера з `/Applications`, копія іншої сесії, будь-що — **не чіпаєш за власною
  ініціативою**.
  **Правило про ЦІЛЬ, а не про механізм.** `kill` одного PID, здобутого через `pgrep`, — та сама
  заборонена дія, що й `pkill`. Акуратний спосіб влучити в чужий процес лишається влучанням у чужий
  процес.
  **Жодна причина, вигадана тобою, не є винятком.** «Заважає автоматизації», «щоб лишився один
  процес», «на секунду, потім перезапущу», «мені так зручніше перевірити» — усе це не підстава, а
  опис того, як саме правило порушують. Якщо перевірка не виходить без вбивства чужого процесу —
  **перевірку віддають мейнтейнеру**, а процес лишають жити.

  ✅ **Єдиний виняток — явне прохання мейнтейнера в цій сесії.** Коли він просить **перевстановити,
  оновити, перезібрати чи перезапустити встановлений застосунок** (`/Applications/TokenPace.app`) —
  «перевстанови», «онови мою копію», «постав свіжий білд», «перезапусти застосунок» або
  еквівалент — **роби це без переспитувань**, і дозвіл покриває **весь ланцюжок**, якого це
  вимагає: зупинити стару копію (за її PID), перезаписати/замінити бандл у `/Applications`,
  запустити нову. Це той самий випадок, що й окреме правило «не збирай dev-`.app` у
  `/Applications`» вище: заборонено **самовільно**, дозволено **на прохання**.
  Межі винятку: дозвіл діє на **конкретне прохання**, а не на всю сесію наперед; він не поширюється
  на копії **інших сесій** і не перетворює «мейнтейнер попросив перевірити фічу» на «можна вбити
  його застосунок, бо так зручніше перевіряти». Просив перевстановити — перевстановлюй; просив
  перевірити — процес не чіпай.
- 🚫 **Запустив на перевірку — не зупиняй, доки мейнтейнер не сказав, що подивився.** Це стосується
  **власного** інстансу теж, і саме тут правило вище має прогалину: воно бережене чужі процеси, але
  щойно агент сам запустив білд «щоб мейнтейнер глянув», той процес перестає бути його — він уже
  **чужий інструмент перевірки**. Перезапуск заради власного скріншота, ретраю, «свіжого логу» чи
  «зараз підніму ще раз» **вбиває чужу сесію перегляду**: людина дивиться на віджет, а він зникає з
  бару посеред огляду.

  Тригер простий: якщо у відповіді пролунало «запусти», «покажи», «перевір», «подивлюсь» — процес
  переходить у режим **hands-off** до явного слова мейнтейнера («бачив», «ок», «стоп», «запусти
  інший стуб»). Хочеш іншу конфігурацію — **спитай**, а не перезапускай мовчки. Не можеш зняти
  скріншот сам (наприклад, `screencapture` повертає порожній кадр без статус-айтемів) — **це не
  підстава для рестарту**: скажи про це й віддай перевірку мейнтейнеру, залишивши процес живим.

  Витік цього правила — сесія, де агент двічі перезапустив власний dev-білд заради скріншота саме
  тоді, коли мейнтейнер розглядав бар на екрані.
- **Ніколи не роби broad-kill** на кшталт `pkill -f TokenPace` / `pkill -f tokenpace` /
  `killall`. Зупиняй **лише той інстанс, який ця сесія сама запустила**, за його **конкретним PID**,
  збереженим при старті (`$!` від власного `&`/`open`-запуску → у файл; `kill "$(cat …)"`).
  **Це стосується й pattern-match за шляхом бандла** (`pgrep -f 'build/TokenPace.app' | kill`,
  `pgrep -f '\.build/debug/TokenPace'`): він зіставляється з інстансами **інших сесій та власними
  інстансами користувача**, а не лише з «застарілими dev-PID». Тож **без явного підтвердження
  мейнтейнера не вбивай за шляхом/іменем — лише за власним збереженим PID.**
  **Чому:** (а) мейнтейнер дивиться логи через `log stream --predicate 'subsystem ==
  "com.artem-n.tokenpace"'` — pattern-kill за іменем зіставиться з цим процесом (предикат містить
  subsystem-рядок) і вб'є моніторинг разом із застосунком; (б) паралельні сесії та реальні інстанси
  користувача не мають гинути від чужого cleanup.
- **Не запускай власний `log stream`, що конкурує з мейнтейнеровим.** Для власної діагностики
  використовуй `log show --last <вікно>` — так його `log stream` лишається живим.
### Цикл «змінив → подивився»: один стрім, N перезапусків

Готовий рецепт. Роби так, не винаходь свій — числа під ним із сесії
[#375](https://github.com/artem-from-ua/tokenpace/pull/375), де свій цикл коштував ~150 із 321
bash-виклику.

⚠️ Цикл описує **власну** діагностику — коли на застосунок дивишся ти. Щойно білд віддано
мейнтейнеру на перегляд, діє hands-off-правило вище: `kill` з кроку 2 **не виконують**, доки він не
скаже, що подивився.

```sh
# 1. ОДИН раз на всю діагностику:
/usr/bin/log stream --predicate 'subsystem == "com.artem-n.tokenpace"' \
  --level debug --style compact > "$TMP/tp.log" 2>&1   # у фон
# 2. Кожна ітерація — лише застосунок:
kill "$(cat "$TMP/app.pid")" 2>/dev/null              # свій PID, збережений при старті
swift build && swift test                             # ОДНА команда, не дві
TOKENPACE_STUB=… swift run & echo $! > "$TMP/app.pid"
until pgrep -qf '\.build/.*/TokenPace'; do sleep 1; done
# 3. Нові рядки — з того самого файлу, що росте:
tail -20 "$TMP/tp.log"
```

- **Стрім не перезапускають.** Він не є станом ітерації. Кожне вбивство власної фонової задачі
  вертається нотифікацією `exit 143/144` — «failed», яку треба прочитати й на яку йде хід. У #375
  так згоріла **51 задача з 60**.
- **`sleep` не чекає — він вгадує.** Пиши `until <перевірка>; do sleep 1; done`: повертається, щойно
  умова справдилась, замість платити найгірший випадок. У #375 **45** команд починались із голого
  `sleep`, і 17 із них — той самий `sleep 4` перед `swift run`.
- **Голий таймер у фоні (`sleep 120; echo waited`) — те саме порушення, іншими словами.** На власну
  фонову задачу чекають через `run_in_background`, на умову — через Monitor з until-циклом.
- **`swift build && swift test` — одна команда.** Дві окремі подвоюють ходи без нової інформації: у
  #375 **17 збірок** пройшли взагалі без нових правок, а об'єднати вийшло лише 5 разів із 24.
- **Пиши `/usr/bin/log`, ніколи не `log`.** Zsh-функція `log` у профілі мейнтейнера перекриває
  бінарник, і команда падає з `(eval):log:1: too many arguments` — повідомленням, яке не натякає на
  причину. Правило вже було тут і все одно порушувалося: скопіювати з пам'яті коротку форму легше,
  ніж згадати про пастку, тож **у прикладах нижче й у CLAUDE.md форма завжди повна**.

## Діагностика layout-багів у вікнах

Правила, кожне з яких виросло з реальної втрати часу в [#346](https://github.com/artem-from-ua/tokenpace/issues/346)
(пів сесії гіпотез, шість раундів верифікації мейнтейнером, зіпсований його фрейм вікна).

### STOP: перші два кроки, до жодної правки

**Тригер цього гейту** — будь-яке повідомлення про те, що елемент UI «з'їхав», «зсунувся», «стоїть не
там», «на пікселі», «трохи праворуч/ліворуч/вище», зокрема з формулюванням «мабуть та сама проблема,
що ми вже фіксили». **Особливо** коли мейнтейнер сам назвав причину: його гіпотеза — це опис
симптому, не діагноз, і погодитися з нею без заміру означає пропустити обидва кроки нижче.

Гейт спрацьовує **до** читання решти розділу і **до** відкриття файлу з підозрюваною в'юшкою. Якщо
перше, що ти зробив у відповідь на «з'їхало», — це `Edit`, ти вже порушив протокол.

1. **Порівняй рядки.** Візьми текст у стані «до» і в стані «після» й подивись, чи він **той самий**.
   Це один погляд, нуль збірок.
2. **Тоді — замір живого дерева** (проба нижче). Не раніше, і не «замір замість правки, якщо правка
   не спрацює».

**Чому саме так, а не «спершу гіпотеза».** Правила цього розділу вже існували й були порушені:
у сесії про «at 20:00 написи з'їзжають праворуч» правка пішла в першому ж ході, проба — на третьому
раунді, після двох білдів, відданих мейнтейнеру зі словами «подивись». Замір потім показав, що
геометрія **бездоганна** (`3h at 16:00` → 77.0 pt, `resets in 3h at 16:00` → 132.0 pt, обидві цілі,
правий край `284.0` в обох станах), а рухалася середина рядка, бо ⌥ додає префікс. Обидві правки
лікували дріб, якого в тому місці не було, і були відкочені. Ціна порушення — три раунди замість
одного.

### Субпіксельна фаза йде від РЯДКА, не від layout — лагодь текст, а не геометрію

Найдорожчий висновок цієї сесії: **шість** правок layout поспіль дали нуль, бо джерело було не там.

- **Симптом.** Текст у бейджі не зсувається, а «дихає»: XOR показує тіло літер чорним, світяться
  лише 1–2 тонкі контури. Заміряно 0.075 pt.
- **Причина.** Фаза (на який субпіксель ляже перший глиф) визначається **послідовністю символів**:
  `5d on Monday` починається з `5`, `resets in 5d on Monday` — з `r`. Різні глифи → різний старт.
  Text renderer це робить, і layout до цього не дістає.
- **Доказ, що це не наша анатомія.** Побудуй канонічний AppKit-бейдж — лейбл у контейнері, падінг
  **констрейнтами**, ціла капсула, жодної кастомної `NSTextFieldCell`, нічого переозначеного — і
  зміряй фазу. Вийде **та сама** `Δphase` (заміряно: 3 quarter-points в обох анатоміях). Тобто перш
  ніж переписувати в'юшку, перевір канонічним варіантом, чи вона взагалі винна.
- **Що НЕ працює** (усе заміряно, не вгадано): `ceil` ширини капсули (0.074 → **0.426** pt, гірше);
  `ceil` ширини контенту через trailing kern (Δtrail 0 → 2); `firstLineHeadIndent`; half-point снап
  `intrinsicContentSize`; переозначення `titleRect(forBounds:)` та `drawingRect(forBounds:)`;
  власне малювання рядка з округленим origin. **Останні три — мертвий код:**
  `NSTextFieldCell` не кладе текст через ці API, піксельний рендер показує нуль різниці.
- **Статус: НЕ виправлено, дванадцять підходів відкинуто.** Ця сесія закрила лише зсув правих
  **лейблів** (`alignment = .right` в `addSplitRow`, дрейф 0.167 → 0.000 pt, підтверджено XOR'ом і
  мейнтейнером). Бейдж лишився в вихідному стані — усі правки до нього відкочені, бо кожна або нічого
  не змінювала в живому рендері, або робила гірше. Остання спроба (`ceil(advance) − cellOwnInset`)
  **обрізала останню літеру** в капсулі, і це помітилось лише коли агент нарешті зробив скріншот і
  подивився сам, а не звітував числами проби.
- **Як перевіряти, що бейдж полагоджено.** Два кадри (⌥ вниз / вгору), вирівняти по **правому** краю
  капсули, XOR. Зараз спільний хвіст `5d on Monday` світиться повним контуром кожної літери
  (заміряно: максимум 121, 77 колонок зі 95). Полагоджено = той хвіст **чорний**.
- **Числа проби ≠ те, що на екрані.** Проба міряла `advance` рядка й давала «LEAD 3.0 / TRAIL 3.0 —
  ідеально», тоді як на екрані текст був обрізаний: реальний ink ширший за advance. **Дивись на
  рендер**, число бери як підказку, а не як доказ.
- **ЩО ДІЙСНО ЗЛАМАНО в бейджі — його розтягує stack, а не падінг.** Жива проба фреймів дала те, чого
  жодна ізольована репліка не показала: `actual − intrinsic = 4.0 pt` на **кожній** капсулі
  (`5d on Monday`, `resets in 5d on Monday`, `active`, `€`), попри `.required` content hugging. Текст
  прибитий до трейлінгу, тож усі 4 pt відкриваються ліворуч — це і є «лівий відступ більше за правий».
  **Починай наступну спробу звідси**: чому `NSStackView` розтягує в'юшку з required hugging, і що
  насправді просить `cellSize` у `PillView.intrinsicContentSize`.
- **Формула `ceil(текст) + 2 × падінг` НЕ спрацювала, хоч і виглядає правильною.** У ізоляції давала
  фазу 0 і рівні щілини; у застосунку — та сама асиметрія плюс повернуте стрибання тексту, бо
  віднімання `2 × cellOwnInset` робить капсулу вужчою за те, що просить комірка, і Auto Layout добирає
  різницю. Урок той самий, що й вище: **ізольована репліка тут систематично бреше**, бо не відтворює
  ні `NSStackView`, ні `edgeInsets` рядка. Міряй у застосунку.
- **Пастка: `cellSize` уже враховує звужений `drawingRect`.** Комірка додає назад те, що забрав інсет,
  тож віднімати `2 × cellOwnInset` не можна — капсула виходить вужчою, ніж комірка просить, і Auto
  Layout розтягує її назад (заміряно: рівно ті 4 pt перекосу). Але й `cellSize + 2 × падінг` дає
  подвоєння. Що саме тут правильно — **не з'ясовано**; це і є ядро відкритого дефекту.
- **Що НЕ працює, хоч і здається симетричним.** Просто вирівняти праворуч, лишивши ширину як була:
  весь добір округлення падає **ліворуч**, і це одразу видно оком (мейнтейнер: «замалий відступ
  праворуч на червоному бейджі і на сірому валютному», далі «дуже несиметричні відступи»). Пів-пункт
  замість цілого пункта (`(w*2).rounded(.up)/2`) — фаза знову 3. Звуження `drawingRect` на половину
  добору — фаза 3. Центрування з «рівним цілим зазором» — фаза 3.
- **Не «прибирай зміну рядка» як фікс.** Спокуса тримати короткий підпис під ⌥ виглядає елегантно
  (причина зникає, XOR чорний) — і була відкинута мейнтейнером: **консистентність ⌥ важливіша**.
  ⌥ розгортає **всі** підписи одразу (ADR-0098), і елемент, що лишився терсим, читається як зламана
  поверхня. Мерехтіння й неконсистентність — не «менше й більше зло», а два дефекти: лагодь обидва.
- **Чому в Apple такого не видно.** Їхні поверхні рідко переписують підпис іншим рядком у тій самій
  позиції — але це не дозвіл копіювати обмеження. Якщо наш дизайн підміняє текст, то саме layout
  мусить бути таким, щоб глифи все одно падали на ту саму сітку.

### «Занадто дрібно, щоб лагодити» — не аргумент у цьому проєкті

Агент, спаливши кілька спроб на баг у 0.075 pt, написав «не виправляється дешево» і запропонував
закрити його issue. Мейнтейнер відкинув: **це macOS-застосунок, тут дизайн на першому місці.**

- **Ціна пошуку ≠ вердикт задачі.** «Я витратив пʼять спроб» описує агента, а не баг. Не подавай
  свою втому як технічний висновок і не проси закрити дефект issue, якщо мейнтейнер його бачить.
- **Ледь помітне дратує сильніше за явне.** Формулювання мейнтейнера: «ледь помітно і тому дратує
  ще більше». Око не знає, *що* змінилося, лише що елемент не тримається — і це гірше за чесний
  зсув на пункт. Мала амплітуда не знижує пріоритет, вона підвищує неприємність.
- **«Це нормальна поведінка системи» треба доводити, а не припускати.** Субпіксельний антиаліасинг
  справді робить рендер macOS, але з цього **не** випливає, що наш layout не можна побудувати так,
  щоб глифи щоразу падали на ту саму сітку. Доводити мусиш ти — заміром на кожному варіанті, а не
  посиланням на «фундаментальність».
- **Порядок дій, коли дешеві округлення вичерпані:** не закривати, а піднімати шар. Дріб приходить
  від центрування дробової ширини тексту → значить питання не в округленні капсули, а в тому, чи
  взагалі текст мусить центруватися в дробовому просторі (фіксована сітка ширин, ціла ширина
  контенту, інша анатомія бейджа). Кожен такий варіант — окремий замір.

### XOR двох станів — перший інструмент, а не останній

Запропонував мейнтейнер після того, як агент спалив пʼять спроб на детекторах кольору
(«знайди червону капсулу», «знайди білі глифи»), кожен з яких ловив то оранжевий бар, то
антиаліасинг, то власний край кропа. **XOR дав відповідь з першого разу.**

- **Метод.** Зняти два кадри в тому самому положенні вікна, звести в градації сірого,
  `ImageChops.difference`, підсилити (`point(lambda v: v*6)`) і подивитись очима. Нуль порогів,
  нуль класифікації кольору, нічого не треба «знаходити» — усе, що змінилося на екрані,
  світиться; усе решта чорне.
  ```python
  from PIL import Image, ImageChops
  a = Image.open("state_a.png").convert("L")
  b = Image.open("state_b.png").convert("L")
  d = ImageChops.difference(a, b).point(lambda v: min(255, v * 6))
  ```
- **Як читати результат.** Це і є діагноз, не проміжні дані:
  - **усі глифи світяться парними контурами** → текст реально зсунувся, шукай геометрію;
  - **світяться 1–2 літери тонким контуром, тіло літер чорне** → глифи стоять піксель у піксель,
    змінилося лише субпіксельне покриття — це антиаліасинг на дробовій ширині, а **не** наш баг;
  - **чорно всюди, а око бачить зсув** → ти знімаєш не той елемент або не ті два стани.
- **Чому це перемагає детектор кольору.** Детектор вимагає знати, *що* шукати, і кожен порог —
  нова гіпотеза, яку теж треба верифікувати. XOR не питає нічого: він показує саму зміну.
  У цій сесії підсумок був 5:1 не на користь детекторів.
- **Дві пастки, обидві траплялися.** Кроп мусить вміщати **обидва** стани: коротший рядок влазив,
  довший обрізався по лівому краю — і агент прочитав власний артефакт як «зсув на кілька пікселів»,
  хоча замір давав 0.075 pt. Мейнтейнеру довелося поправляти («не може бути кілька пікселів»).
  І вирівнюй кадри по **запіненому** краю (у попапі — правому), інакше різна ширина елемента сама
  дасть суцільне світіння.
- **Профіль яскравості як підтвердження.** Той самий висновок числом: узяти смугу всередині
  елемента й вивести максимум яскравості по колонках. Напівтон там, де в іншому стані чистий фон
  (заміряно: 115 → 170 на тлі фону 115 і глифа 254), означає, що край літери зайшов на піксель
  частково — субпіксель, не зсув.

### Зсув при ⌥ має ДВА механізми — дешевший не піксельний

- **Спершу порівняй рядки, тоді геометрію.** ⌥ не «підсвічує той самий підпис» — воно **підмінює його
  розгорнутим** (`3h at 16:00` → `resets in 3h at 16:00`, `18d` → `resets in 18d`,
  [ADR-0098](../adr/0098-ruler-split-identify-always-explain-on-option.md)). Права колонка при цьому
  тримається (пінена flush right), тож рядок росте **вліво**, а вся його **середина** їде на цілі
  пункти. Око, що дивиться на час, читає це як «час зсунувся» — і опис симптому звучить ідентично
  субпіксельному дефекту. Різні тексти → це **не** баг геометрії, і жодне `ceil` не поможе; питання
  стає продуктовим (що тримати нерухомим: правий край чи саме число).
- **Однакові тексти + різна геометрія** → аж тоді дріб, і далі за розділом про #374 нижче.
- **Ознака, що ти лікуєш не те:** замір показує цілі числа й однаковий правий край, а зсув на екрані
  лишається. Стоп — механізм не знайдено, назад до порівняння рядків.

### Правила заміру

- **Спершу замір живого дерева, потім гіпотези.** Правдоподібних пояснень у layout-бага завжди
  кілька, і кожне вбивається одним заміром — тож замір дешевший за будь-яку з теорій. Тимчасовий
  env-gated хук у `App.swift`, який щосекунди пише в файл (`TOKENPACE_PROBE_FILE`): для кожного
  `NSScrollView` — frame у координатах вікна, `contentInsets`, `automaticallyAdjustsContentInsets`,
  `documentView`/clip висоти, скролер; для підозрюваного — **ланцюжок предків до кореня** з
  розмірами (саме він у #346 показав, що інфляцію дає перший же SwiftUI-нащадок хостинга). Міряти
  мінімум на **двох висотах вікна**. `print` не годиться (stdout буферизується в фоновому запуску),
  `log`-команди в цьому shell ламаються об профіль — файл надійний.
- **Діагностика read-only до стану користувача.** Проба НЕ сміє викликати `setContentSize` /
  `setFrame` / рухати вікно: `windowDidResize` персистує фрейм, і тест мовчки перезаписує розмір,
  який виставив мейнтейнер (сталося в #346 — двічі). Розміри міняє лише людина; проба семплить
  таймером.
- **Людині віддають лише число-верифіковані білди.** Перед «подивись» — проба: цільові числа
  зійшлися → тоді око мейнтейнера перевіряє естетику, а не шукає механізм. Ітерації «збери-подивись»
  об живу людину — найдорожчий цикл у проєкті.
- **Скріншоти придатні для вимірів layout, не лише «побачити».** Масштаб виводиться з відомої
  величини в кадрі (ширина вікна запінена — 792/857 pt) → px/pt → різниці відступів рахуються з
  уже надісланих скріншотів без нового раунду. Заборона стосується лише **кольорів**
  (див. [ui-verification.md § «Тестування кольорів menu-bar віджета»](ui-verification.md#тестування-кольорів-menu-bar-віджета-swatch-режим--піпетка)).
- **SwiftUI дивно поводиться біля window chrome → першим перевір межу хостингу.** У цьому репо
  вікна — AppKit-shell зі SwiftUI-вмістом ([ADR-0009](../adr/0009-statusitemview-pure-layout-and-thin-shell.md)),
  і контракт `NSHostingController` (`sizingOptions`, `safeAreaRegions`, `contentLayoutRect`)
  впливає на layout сильніше за будь-який SwiftUI-модифікатор. У #346 шість варіантів
  margins/padding програли одному рядку `safeAreaRegions = []` —
  [ADR-0088](../adr/0088-settings-hosting-safe-area-and-manual-separator.md).
- **Бінарний підбір константи об скріншоти = механізм не знайдено.** Якщо число доводиться
  підганяти (17→32→24→28…), латається симптом не в тому шарі — стоп, назад до заміру.
- **Висновок у докблок чи звіт — лише після верифікації.** Формулювання «працює як у системі»
  до живої перевірки мейнтейнером — це обіцянка, не факт; пиши «очікується/за замiром», доки
  людина не підтвердила.

### Зсув на пів пункта: шукай дробову висоту, а не винну в'юшку

Виросло з [#374](https://github.com/artem-from-ua/tokenpace/pull/374): весь вміст попапа з'їжджав на
**0.5 pt** при натисканні ⌥, у прев'ю поряд із Settings і **не** в реальному дропдауні. Пішло сім
хибних спроб, дві з яких зламали робоче прев'ю, перш ніж знайшлася причина.

- **Скануй дерево, не вгадуй в'юшку.** Тимчасовий обхід піддерева, що логує кожну в'юшку з нецілим
  `intrinsicContentSize` / `fittingSize` / `frame`, знаходить винуватця за один прохід. Усі сім
  спроб до нього били по **лейблах** — а дріб був у зовсім іншому місці. Шаблон:
  ```swift
  let frac = { (x: CGFloat) in x > 0 && x != x.rounded() }
  // рекурсія по subviews, логувати лише висоти — ширини дробові по всьому попапу й вертикалі не рухають
  ```
- **Дріб дає похідна метрик шрифту, а не сам текст.** По **висоті** `NSTextField` округлює власні
  метрики до цілих (13 pt → рівно 16.0, з текстом і без) — тут лейбли не є джерелом. Дробове дають:
  **SF Symbol в `NSImageView`** (заміряно: `hand.raised` 16, `clock` 15.5,
  `exclamationmark.triangle` 16.5) і **власні обчислення з `ascender`/`descender`/
  `boundingRectForFont.height`** (наш `PopupBarView.creditsViewHeight` давав 25.5). Кожну таку
  формулу закінчуй `ceil(...)`.
- **По ШИРИНІ лейбли — теж джерело дробу, попри попереднє формулювання тут.** Заміряно пробою в
  попапі: `intrinsicContentSize.width` цих самих полів стабільно `.5` (`on pace` 48.5,
  `limit reached` 78.5, `well ahead of pace` 113.5, `18d` 22.5), `fittingSize` додає 4 pt padding
  комірки й лишається дробовим (52.5, 82.5, 117.5). Ця сторінка раніше стверджувала «лейбли **ніколи**
  не є джерелом» без уточнення про вісь — і це твердження, продубльоване в коментарі до `makeHandChip`
  у `PopupViewController.swift`, само повело діагностику не туди. **Мораль ширша за факт: твердження в
  докблоці — не замір.** Якщо правило каже «X ніколи не буває причиною», а симптом указує на X — міряй
  X, а не вір рядку.
- **Констрейнт вішай на в'юшку, а не на рядок.** `NSStackView` створює вирівнювальні констрейнти з
  пріоритетом `NSLayoutPriorityDefaultLow` і документує їх як «overridable for individual views using
  external constraints» (`NSStackView.h`). Тому `heightAnchor` на рядку програє intrinsic-розміру
  вмісту, а той самий констрейнт на самій в'юшці працює. `alignmentRectInsets` теж не поможе —
  `NSStackView` розкладає arranged-в'юшки за frame і його ігнорує (виміряно, див. `addSplitRow`).
- **`backingAlignedRect` тут шкідливий.** Це API пікселного снапу, і на Retina його сітка сама
  **0.5 pt** — 16.5 він збереже, а не виправить. Для цілих пунктів потрібен `ceil`.
- **«Видно лише в одній поверхні» — не магія тієї поверхні.** Дропдаун ховає дріб, бо
  `NSMenuItem.view` отримує явний frame із `fittingSize` один раз; вікно з Auto Layout тягне дріб
  далі по вертикальному стеку. Apple **не** документує жодного округлення в `NSMenu` — тож лагодь
  джерело, а не поверхню, інакше друга поверхня лишиться зламаною.
- **Не чіпай розмірювання прев'ю навмання.** Спроби нав'язати йому менюподібну модель
  (явний констрейнт висоти попапа) двічі зламали вікно — спершу схлопнули вміст до плашки, потім
  розсипали його під ⌥. Виправляй дріб у джерелі; модель хостингу лишай як є.

## Issues та GitHub Project

- Після `gh issue create` **одразу додай issue до GitHub Project мейнтейнера й постав Status** — не
  лишай його поза дошкою.
- Процес: дві GraphQL-мутації — `addProjectV2ItemById(projectId, contentId)` (повертає item id;
  `contentId` — node id issue), потім `updateProjectV2ItemFieldValue(...singleSelectOptionId)` для
  Status.
- Status за станом issue: **open → Todo**, **closed → Done** (In Progress — лише коли активно в
  роботі).
- Конкретні node-ID проєкту/поля/опцій — приватні й зберігаються поза репозиторієм; якщо мутація
  падає — перевір їх заново (проєкт могли відредагувати).

## «Docs are part of code»

Зміна в тому самому коміті, що й код:

- Зміна модуля → онови [architecture.md](../architecture.md).
- Рішення між двома підходами → новий ADR у [../adr/](../adr/).
- Зміна логування (новий/видалений виклик, інший текст/рівень/категорія) → онови
  [log-messages.md](../reference/log-messages.md) у **тому самому** коміті.
- Нова конвенція/інструмент → онови [conventions.md](../reference/conventions.md).
- Нова фіча зі своїм станом → додай стуб і онови таблицю стубів у [ui-verification.md](ui-verification.md).

## Верифікація перед PR

- **Не відкривай PR і не кажи «готово», доки мейнтейнер не перевірив зміну вживу** — на стубах
  та/або на реальній даті.
- **Скриншоти з тимчасового dev-only коду не рахуються** за верифікацію (синтетичний рендер доводить
  лише логіку малювання, не роботу в живому віджеті/Settings/потоці даних).
- Робочий цикл: коміт у feature-гілку → `swift build` → віддати мейнтейнеру → підтвердження → PR.

### Доки й ADR пишуться ПІСЛЯ того, як мейнтейнер побачив фічу вживу

Повний порядок: **код → `swift build`/`swift test` → скриншоти мейнтейнеру → його підтвердження →
доки/ADR → PR.** Ланка доків стоїть саме тут, а не раніше, і це не формальність.

Писати ADR до підтвердження — марна робота. ADR фіксує не лише *що* зроблено, а *чому обрано цей
підхід*; якщо після живої перевірки поведінка зміниться, переписувати доведеться не тільки код, а й
обґрунтування рішення — тобто найдорожчу частину документа. Те саме з
[architecture.md](../architecture.md) і [log-messages.md](../reference/log-messages.md): вони
описують те, що лишилося після перевірки, а не те, що планувалося до неї.

Це **не** послаблює правило «[docs are part of code](#docs-are-part-of-code)» вище: доки й код
однаково їдуть **в одному PR**. Йдеться лише про момент, коли їх писати всередині циклу — після
підтвердження, а не до нього.
