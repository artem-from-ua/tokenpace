> **Postscript (ADR-0043, #167):** decision **D5** below is superseded — the `TimeToReset.resetNow`
> state is **removed**, rather than kept as a safety net. Its three sources are now resolved
> explicitly: `remaining ≤ 0` is rolled forward (`optimisticReset` is applied on **every** render, not
> only by the timer — eliminating the sub-second race), a broken `resets_at` on the selected noisy
> window → the ⚠️ error state, and the error-branch fallback → no countdown. The rest of the decisions
> (D1–D4, D6) still stand. See [ADR-0043](0043-unified-reset-line-and-remove-resetnow.md).

# ADR-0030: An optimistic reset on an exact timer instead of a passive `.resetNow` state (⏰)

## Context

When a limit's reset time from the last usage payload arrives, but a fresh payload with the new
(future) `resets_at` hasn't been received yet, `ResetClock.timeToReset` returns `.resetNow`
(`remaining ≤ 0`), and the menu bar draws a colored emoji alarm clock **⏰**. Problems:

1. **⏰ breaks the visual style.** The rest of the menu bar is monochrome text/glyphs in
   `labelColor` (compare the ⚠️ error state, which is drawn monochrome). A colored emoji clashes
   sharply (#36).
2. **The "resetting…" state is visible longer than it should be.** `.resetNow` occurs **passively**
   at render time, and renders are generated by the 30-second `ageTimer` and polling ticks (60 s–30
   min). Nothing "wakes up" exactly at the `resets_at` instant, so ⏰ can hang around for seconds to
   minutes, until the next poll brings a fresh `resets_at`.

A mechanism for forcing an out-of-band request already exists — `PollSignal.manualRefresh` (the
Troubleshoot → `AppDelegate.forceRefresh` button) resets the 429 backoff and does an immediate poll.
All that was missing was a trigger exactly at the reset instant and a local "placeholder" for the
time until the response arrives.

## Decision

Instead of passively showing ⏰ — **an optimistic reset on an exact timer**.

- **D1. An exact one-shot timer.** `AppDelegate.resetTimer` — a non-repeating `Timer`, scheduled
  exactly at the nearest **future** `resets_at`
  (`ResetClock.nextResetInstant(fiveHourResetsAt:sevenDayResetsAt:now:)` across both windows).
  Rescheduled on every `apply(_:)` (against the fresh API `resets_at`) and on wake; invalidated on
  sleep. `.common` run-loop mode — to fire during menu tracking (like `ageTimer`). The passive
  render-time detector is **not** used.

- **D2. A local optimistic reset.** At the moment it fires, `fireOptimisticReset` rolls the last
  snapshot forward through a pure `ResetClock.optimisticReset(_:now:)`: every window with
  `resets_at ≤ now` → `utilization = 0` + the next window; a window still in the future is left
  untouched. Per-window rules:
  - **5h:** `sessionIdle` → stays idle (`utilization: 0`, `resets_at: ""`); an active 5h past its
    boundary → `utilization = 0` + a synthesized `resets_at = now + 5h`.
  - **7d:** past its boundary → `utilization = 0` + `resets_at = now + 7d`; sub-windows
    (`Opus`/`Sonnet`) reset along with 7d, borrowing its new `resets_at`.
  - **`limits`** — unchanged (a temporary overlay; the next successful poll overwrites it anyway).
  Driven by **comparing `now` against each window's `resets_at`**, not "which window fired" — robust
  against coinciding 5h+7d resets and against timer drift.

- **D3. Order and source of truth.** `fireOptimisticReset`: (1) replaces `lastOutput` with the
  overlay and **immediately** renders (the menu bar updates at once, with no ⏰); (2) reschedules the
  timer for the next boundary; (3) sends `.manualRefresh` (`forceRefresh`) — the forced poll goes
  through the engine, so backoff/health update normally. **The API is the source of truth:** any
  successful response fully overwrites the overlay (even if the usage there is > 0); on 429/error the
  overlay holds until the next success. A `reset != snapshot` guard in `fireOptimisticReset` protects
  against an early/spurious trigger.

- **D4. Resilience to sleep.** `Timer` is unreliable across sleep, so on sleep the timer is
  invalidated, and on wake `rescheduleResetTimer` recomputes the delay from the current `Date()`; if
  the reset happened during sleep, a `delay ≤ 0` guard applies the optimistic reset immediately.

- **D5. `.resetNow` remains as a safety net, but with no ⏰.** The `TimeToReset.resetNow` case is not
  removed — it's still reachable via three independent paths (an unparseable `resets_at` in
  `selectReset`, the error-branch fallback, `remaining ≤ 0`). Only its rendering changes:
  `StatusItemView.resetText` returns a neutral **`"<1m"`** ("about to refresh"), as requested in #36.
  In the normal flow this case is no longer reached — the timer rolls the window to zero first.

- **D6. The seconds strip is removed; minutes are rounded.** The menu bar only redraws on a ~30-s
  cadence (`ageTimer`), so a per-second countdown in the `(0, 60)` s strip jumped roughly (`12s` →
  suddenly a new absolute time) — a visible flaw. So: a sub-minute remainder is now rendered as
  **`"<1m"`** (rather than `12s`/`40s`), and the `[60 s, 90 min]` range is now **rounded to the
  nearest minute** (`relativeString`), instead of truncating down. The popup is aligned:
  `relativeRounded` also gives `"<1m"` under a minute (the threshold shifted from `< 30 s` to `< 60
  s`), so the menu bar and popup no longer diverge. This supersedes the **seconds strip** from
  [ADR-0006](0006-reset-time-absolute-vs-relative.md) (see its postscript); replacing ⏰ with `<1m`
  (rather than `~1m`) is the same unified string.

## A deliberate divergence from #100 / ADR-0027

[ADR-0027](0027-session-idle-no-phantom-reset.md) deliberately **disabled** the local estimate of
`now + 5h` for the 5h window in the decoder (`localEstimateAllowed: false`), because the 5h window
**doesn't exist** until the first token spend creates it — synthesizing one there produced a
"crawling" phantom reset on an **empty** window.

`optimisticReset` synthesizes `now + 5h` only for an **active** 5h window (`sessionIdle == false`)
that has just crossed its own reset boundary — i.e., a window genuinely rolling into a new active
cycle, not an empty idle window. An idle window under ADR-0027 explicitly stays idle here (D2). So
this is **not** a regression of #100: 0027's prohibition applies to the idle case, and 0030's
exception applies to the active case; they don't overlap. The synthesis is a temporary overlay, which
the next successful poll will overwrite with the real `resets_at` anyway.

## Consequences

- The menu bar no longer shows a colored ⏰ during a normal crossing of the reset boundary — the bar
  rolls straight from a live countdown into the fresh window, and a forced poll confirms the state
  within seconds.
- `.resetNow` now marks only genuinely degenerate data (missing/broken `resets_at`) and renders as a
  neutral `"<1m"` instead of an alarming clock — consistent with the menu bar's monochrome style.
- The exact timer adds one non-repeating `Timer` to the coordinator; its resilience to sleep is
  ensured by invalidate-on-sleep + recompute-on-wake (D4).
- Verification — stub `TOKENPACE_STUB=optimistic-reset`: 5h resets ~20 s after start, the bar visibly
  jumps 60% → 0% with no ⏰, followed by a forced refresh.
