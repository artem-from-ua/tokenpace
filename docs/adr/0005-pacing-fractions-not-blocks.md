# ADR-0005: PacingModel — зони у відсотках, не дискретні блоки

> **Частково superseded [ADR-0059](0059-menu-bar-native-semantic-colours.md):** колірна прив'язка
> «PacingState → RGB» (dark_gray=236/green=71/red=167/blue=23, xterm-256 палітра statusline, див.
> «Наслідки») скасована — menu-bar-віджет тепер малює системними semantic-кольорами, а не фіксованим
> sRGB зі statusline. Решта цього ADR (зони як частки [0,1], а не дискретні блоки) лишається чинною.

## Контекст

`statusline.sh` малює pacing-смужку у терміналі як послідовність із N дискретних блоків-символів
(`■`/`■̿`). Функція `build_progress_bar` отримує `u_pct`/`t_pct` у відсотках і квантує їх у
блок-індекси round-half-up: `u_blocks = (u_pct * total + 50) / 100`, де `total` = 28–30 залежно
від вікна. Потім `ind_pos` (4 гілки) визначає, який блок стає індикатором поточного часу.

Issue #6 («PacingModel + unit-тести») формально вимагає «порт `build_progress_bar` 1:1», але
menu bar macOS малює смужку як кастомну `NSView` з піксельним малюванням (`NSBezierPath`/
`NSRect`). У цьому контексті блокова квантизація — **артефакт термінального рендерингу**, а не
доменна логіка.

Розглянуто два підходи:

| | Блоки (дослівний порт) | Відсотки (наш вибір) |
|---|---|---|
| Що повертає модель | `u_blocks`, `t_blocks`, `ind_pos` (цілі) | `usageFraction`, `timeFraction`, `pacing` (Double [0,1]) |
| Чіткість домену | Змішує бізнес-логіку з рендер-артефактом | Чиста геометрія пікселів |
| Якість рендерингу | Стрибки по 1/30 (~3,3 %) | Плавний, субпіксельний |
| Тестовність | Тести прив'язані до ширини бару (30 / 28) | Тести перевіряють реальні відносини use vs time |
| Майбутнє (popup) | Блоки не потрібні у popup-тексті | Можна квантувати через `blockIndex()` за потреби |

Рішення узгоджено з Артемом явно в сесії реалізації issue #6.

## Рішення

`PacingModel` повертає **безперервні частки [0,1]** через `BarLayout`:

- `usageFraction` — частка використання (clamped `utilization / 100`, без truncation —
  піксельний рендер тримає точність).
- `timeFraction` — частка минулого часу вікна (портовано з `calc_time_pct`, але як точна
  `Double`, а не цілочисельно-truncated; розходження < 1 %, на пороги індикатора не впливає).
- `pacing: PacingState` — `.ahead` / `.onPaceOrBehind` (бінарний вибір кольору проміжку,
  точний порт `u_blocks <= t_blocks` dispatch).

Порогова логіка `get_limit_indicator` портується **дослівно**: обидва аргументи truncate-to-int
перед порівнянням (`Int(max(0, x))`), пороги 100 / 90 зберігаються 1:1.

Блокова квантизація зберігається як **опційна похідна** `PacingModel.blockIndex(fraction:cells:)` —
portує `(pct * total + 50) / 100` round-half-up із `build_progress_bar` — для майбутнього popup
(#11), де може знадобитись показ позицій на сітці. У menu bar bar ця функція не викликається.

## Наслідки

- Смужка в menu bar рухається плавно, без стрибків по 3,3 %.
- `StatusItemView` (#10) дістає чисту геометрію: три зони та позицію індикатора як Double [0,1]
  і маплять `PacingState → RGB` (dark_gray=236, bright_green=71, bright_red=167, dark_blue=23).
- `get_limit_indicator` відтворено point-to-point з bash (всі пороги перевірено unit-тестами,
  включно з граничними `99.9999 → нейтрально / 91 && time 90 → попередження`).
- Розходження `elapsedFraction` vs `calc_time_pct` < 1 % — не впливає на будь-який видимий
  threshold; задокументовано в doc-коментарях `PacingModel`.
- `blockIndex` доступний, якщо popup (#11) вирішить показувати блокову сітку; точна кількість
  клітинок передається як аргумент `cells:`, а не зашита в модель.
