# Архітектурні рішення (ADR)

Записи архітектурних рішень проєкту. Кожен **accepted** ADR незмінний; `draft` можна
доопрацьовувати, доки він не став `accepted`. Коли рішення застаріває, його запис лишається, а в
індексі номер і назва закреслюються.

**Повне vs часткове витіснення.** Розрізняємо два випадки, і frontmatter у них різний:

- **Повне** — усе рішення замінене новішим ADR. У frontmatter: `status: superseded` + `superseded_by: [NNNN]`. У таблиці статус — `superseded`.
- **Часткове** — новіший ADR витісняє лише *фрагмент* рішення (напр. один із розділів чи дефолт опції), а решта лишається чинною. Тоді `status` **залишається `accepted`** (рішення здебільшого чинне — ставити `superseded` було б неточно), але додається `superseded_by: [NNNN]`, а вгорі тіла ADR — post-scriptum, що розмежовує, що́ саме витіснено і що́ лишається чинним. У таблиці статус пишеться описово: `partially superseded → NNNN (що саме)`.

В обох випадках номер і назва в таблиці закреслюються. Приклади часткового витіснення — [0025](0025-check-for-updates.md) і [0033](0033-automatic-update-install.md) (обидва частково витіснені [0036](0036-update-signals-single-dropdown-item.md)).

**Чернетки (draft).** ADR, чиє рішення ще *не* прийняте остаточно — воно за гейтом (спайк, дослідження, зовнішня валідація) або описує запропонований, але не реалізований напрям — має `status: draft`. У таблиці статус — `draft`; номер і назва **не** закреслюються (draft не є застарілим). Коли рішення приймається, `draft → accepted` у тому ж файлі — з цього моменту ADR стає незмінним (`draft` — єдиний статус, який дозволено переписувати). Draft, що не злетів, отримує `status: rejected` з одним рядком-причиною. Життєвий цикл: `draft → accepted → (superseded)`, з гілкою `draft → rejected`.
